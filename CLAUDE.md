# CLAUDE.md

Guidance for AI assistants (Claude Code) working in this repository. Human usage lives in `README.md`; this file is the engineering/agent context.

## What this is

`darkubectl` — a kubectl-like CLI for the Hamravesh **Darkube** platform. Go 1.27, built on `urfave/cli/v3` (not Cobra). It talks to the Hamravesh REST API and an exec websocket.

## Build / test / lint

```sh
go build ./...
go test -race ./...
golangci-lint run ./...   # must report 0 issues before committing
gofmt -w .
```

CI (`.github/workflows/ci.yml`) runs `golangci-lint` (v2.13.1) and `go test -race` on push to `main` and on PRs, using the Go version from `go.mod`.

## Architecture

- `cmd/` — the `urfave/cli/v3` command tree. Root + shared helpers in `app.go`; one file per command group (`get`, `describe`, `scale`, `patch`, `delete`, `create`, `set`, `env`, `domain`, `notifications`, `whoami`, `login`, `exec`, `terminal`, `config`). `session.go` holds exec/terminal helpers. Auth is resolved once in `app.go`'s `resolveAuth`.
- `internal/client` — REST client on `resty/v3`. `Auth` is either `APIKey(...)` or `BearerToken(...)`; every request also sends `X-Organization`. `update.go` holds the read-modify-write path every mutation goes through (`UpdateApp`) plus the small accessors (`EnvVars`, `SecretEnvNames`, `ExternalHosts`) that read the raw app map; `profile.go` reads the account and its organizations.
- `internal/auth` — Console JWT mint/refresh (SimpleJWT).
- `internal/wsexec` — exec websocket transport on `coder/websocket`.
- `internal/output` — table / JSON / YAML rendering plus the colorized `describe` view (`lipgloss`; auto-degrades to plain text when not a TTY).
- `internal/tui` — interactive Bubble Tea viewers (the `describe -i` viewer).
- `internal/kube` — reads Deployments out of a cluster by shelling out to `kubectl` (no client-go dependency; inherits the user's kubeconfig, context and OIDC exec-plugin auth) and diffs them against the app list. Backs `get orphans`. `Diff` is pure and unit-tested; only `Deployments` touches the outside world.
- `internal/config` — koanf-based config: `~/.darkube/config.yaml` layered with `DARKUBE_*` env vars (`DARKUBE_ORG` → `current-tenant`, etc.), written 0600.

## The Darkube API (reverse-engineered — official docs are not reachable)

- Base: `https://api.hamravesh.com` — public IP, call it **without** a proxy. The `*.darkube.app` hosts resolve to a private IP and are not usable directly.
- Every request is tenant-scoped by `X-Organization: <org-slug>` (403 `permission_denied` without it). Tenant = organization; namespace = project; app = app.
- REST auth is either scheme: `Authorization: Api-key <k>` **or** `Authorization: Bearer <jwt>`.
- Key endpoints:
  - `GET /api/v2/darkube/apps/?limit=&offset=&fields=` — list; `GET/DELETE /api/v2/darkube/apps/<uuid>/` for one app. The list returns the **full** object, not a projection, so `external_hosts`, `custom_config`, `image_repo`/`image_tag` and `updated_at` are available without an extra fetch per app — which is why `get apps -o wide` can show the running image and how stale it is for a whole namespace in one request. Writes go to v1 (see `PUT` below); `PATCH` is unimplemented at both versions.
  - `GET /api/v1/darkube/plans/` (global), `.../certificates/`.
  - `GET /api/v1/darkube/namespaces/` — paginated DRF list of projects, with `id`, `name` and the nested `cluster`. Needs a **JWT**; the Api-key is rejected, which is why `NamespacesFromApps` exists as a fallback. Prefer `client.Namespaces`, which tries this first: the derived list can only contain namespaces that already hold an app, so a freshly created empty project is invisible to it — exactly when you need its id in order to create the first app in it.
  - `POST /api/v1/darkube/apps/` — **create** (v1, not v2). Body needs `svc` `{type,ports}`, `custom_config`, `builder`, `ssl_challenge_type`, `organization` (numeric id, from an app's v1 detail), `namespace` (int), `plan`. Requires JWT (user context); the Api-key 500s. See `client.buildCreatePayload`.
  - `PUT /api/v1/darkube/apps/<uuid>/` — **the write path**. Takes the whole object and returns 202. Relations must be bare primary keys, not the nested objects a read returns (`plan` as a uuid string, `namespace`/`organization` as ints), or it 400s with "plan: … is not a valid UUID". Server-owned fields have to be dropped: `cluster`, `creator`, `state`, `latest_build`, `workflows`, `deploy_context`, `version`, `updated_at`, `creation_time`, and `secret_envs`. See `client.UpdateApp`, which does the read-normalize-mutate-write cycle so callers change one field without rebuilding the other seventy.
  - `GET /api/v1/darkube/apps/<uuid>/app_log/` — container logs. Query: `pod_name`, `container_name`, `previous` (the crashed instance, like `kubectl logs -p`), and an index window `from_index`/`to_index` anchored by `reference_index`. The window is absolute, not time-based; the server clamps an out-of-range window to the end, so the tail is `from_index=20000000` (the console's own sentinel) and `to_index=20000000+N`. Response is `{"logs": {"<rfc3339>": "<text>"}, "reference": <int>}` — an **object**, so ordering is lost in JSON and has to be restored by sorting the keys. Entries can hold several physical lines separated by ` \n `.
  - `GET /api/v2/users/profile` — the signed-in account. **The only endpoint that lists organizations**: no `/organizations/` route exists at any version (all 404), and this one is *not* tenant-scoped, so it answers "which tenants exist" before an `X-Organization` is known. Each entry carries the numeric `id` the app-create payload wants as `organization`, plus `current_user_roles`, `available_clusters` and `owned_domains`. Note the prefix — `/api/v2/users/`, outside the `/api/v1/darkube/` tree, which is why it evades every probe of that tree. Backs `whoami` and `client.OrganizationID`.
  - `GET /api/v1/notifications/all_list/?limit=&offset=` — the account's notification feed (DRF-paginated). Spans **every** organization the account belongs to, so it ignores `X-Organization`. Persian prose; `description` carries HTML.
  - `GET /notifications/alerts/api/alerts/` — monitoring alerts for the tenant. Note the prefix again: served from `/notifications/alerts/api/`, outside `/api/v1/`, and it answers with a **bare JSON array**, not the DRF `{count,results}` envelope.
  - `POST /api/v1/token/` — `{email,password}` + TOTP → `{access,refresh}`.
  - `POST /api/v1/token/refresh/` — `{refresh}` → `{access}`.
  - `OPTIONS` on any endpoint returns the **DRF metadata**, including per-field `required`/`read_only`/`type` for the write serializer and the allowed write methods in `actions`. This is the fastest way to map a surface — it is how the PUT-not-PATCH discovery was made. Treat it as indicative rather than binding: the list route's OPTIONS marks `organization` read-only and `secret_envs` read-only, yet POST demands the first and persists the second.
  - `wss://api.hamravesh.com/ws/aexec/?app_id=&pod_name=&container_name=` with `Sec-WebSocket-Protocol: terminal, <jwt-access>, <org>` and `Origin: https://console.hamravesh.com`.
  - `wss://api.hamravesh.com/ws/app-pods/?app_id=` with subprotocol `json, <jwt-access>, <org>` — streams pods as JSON; the **only** source of pod names (REST `state.pods` is empty; `/ws/app-state/` carries only aggregate replica counts). Parsed in `internal/appstate`. The `app_pods_update` frame carries far more than names: per pod `namespace`, `phase`, `text`/`state_type`, `is_ready`, `is_terminating` and `creation_time` (a space, not RFC 3339's `T`, so `time.RFC3339` alone will not parse it), and per container `is_ready`, `restart_count` and `last_state` `{state,reason,message}`. That is the **only** place a crash loop is visible: REST reports the app as a flat "not ready" no matter how many times the container has died, so `get pods` reads READY/STATUS/RESTARTS/AGE from this frame.
- **App detail fields worth knowing** (from `GET .../apps/<uuid>/`). These can be set at `POST` and changed afterwards with `PUT`:
  - `disk` — `{partitions:[{display_name,mount_path,sub_path}], set_fsgroup, size_in_Gi, storage_class_name}`. `storage_class_name` is **required**: omitting it returns 500, not a validation error. `rawfile-btrfs` is valid on c11 and c13.
  - `svc` — `{type, ports:{<name>:{containerPort,servicePort,nodePort,protocol}}}` plus read-only `internalAddress` / `externalIP`. Omit `ports` and the app exposes nothing.
  - `envs` / `secret_envs` — lists of `{name, value}`. The key is `name`, not `key`; `key` returns a bare 400 `invalid` with an empty `detail`. **`secret_envs` changes type by route**: the v2 *list* types it as a bare vault-path string and carries the names in a separate `secret_envs_keys`, while v1/v2 *detail* returns `[{name, value}]`. Anything typing it as a slice fails to decode the list; `client.SecretEnvNames` reads both shapes. Secret **values are never returned** — every entry reads back empty, because they live in a vault (`console/data/production/darkube/StatelessApp/<app-id>/secret_envs`). So there is nothing for a `--show-secrets` flag to reveal, and secrets can only be written at `POST` — they are read-only on the PUT serializer, which is why `UpdateApp` drops the field rather than echoing it (echoing it risks clearing them).
  - `external_hosts` — **the domain list, and where custom domains actually live.** A plain `[]string`, writable. `custom_domain_address` is a different, usually-null field and is *not* the ingress host list: `sepid-website` serves `sepid.org` from `external_hosts` while its `custom_domain_address` is null. Alongside it: `ingress_annotations`, `ingress_labels`, `ingress_class_name`, `ingress_basic_auth_config`, `enable_SSL`, `redirect_SSL`, `enable_httpv2`, `ssl_challenge_type`, `certificate_ids`, and read-only `ingress_cname_address` — the CNAME target a domain's DNS must point at (e.g. `c11.hamravesh.onhamravesh.ir`). Backs `get domains` / `set domain`.
  - `custom_config` — the app's **Helm chart values**, and it is **silently filtered against the chart's schema**: unknown keys are dropped with no error and no warning. For a docker-image app the allowlist is narrow — `hpa` (`{enabled,minReplicas,maxReplicas,targetCPUUtilizationPercentage}`) and `container` (`{readinessProbe,livenessProbe}` with full k8s probe shape including `httpGet.httpHeaders`) survive; `config`, `serviceType` and anything invented are stripped. `is_hpa_enabled` is derived from `custom_config.hpa.enabled`. Note it is **ignored entirely at `POST`** for a docker-image app (it comes back null) and has to be set with a follow-up `PUT`.
  - `custom_config.config.files` — `{"<filename>": "<file body>"}`, the ConfigMap-through-the-chart mechanism. It works **only on marketplace/chart-backed apps** whose chart defines it (confirmed on the redis and postgres charts: `redis.conf`, `sentinel.conf`, `postgresql.conf`). On a docker-image app it is stripped by the filter above, so there is **no way to mount an arbitrary config file into a plain app** — use `envs` instead, or bake it into the image.
  - `command` / `args` — **not symmetric, and this is the sharpest edge in the API.** `command` is SPLIT on whitespace into argv; `args` is passed through as a SINGLE argv element and is never split. Established by experiment on 2026-08-27, because nothing documents it and no app in any reachable tenant used either field. The consequence: the arrangement everyone writes first, `command: /bin/sh` + `args: -c <script>`, hands the container `argv[1] = "-c <script>"` as one token, and busybox reads the space after `-c` as another flag — `/bin/sh: illegal option -`, crash-looping, with nothing in the API response pointing at the cause. The working form is `command: "/bin/sh -c"` + `args: "<script>"`, and because `command` is split the script must then contain no whitespace at all (`$IFS` supplies separators after splitting has happened). `cmd/appargs.go` warns on whitespace in `args` and rejects a multi-element `args` list; `cmd.entrypointWarnings` is the one place that explains it at the moment it can still be acted on.
  - `custom_subdomain_addr` — the app's subdomain **on the cluster's own domain** (`cluster.apps_custom_base_domain`, usually `darkube.app`), as a bare label. Distinct from `external_hosts`, and the two are not interchangeable: adding `<label>.darkube.app` to `external_hosts` is rejected with `400 InvalidExternalHost` and a Persian detail that does not say which of the two you wanted. Setting this instead makes the platform host the name and issue a certificate over the `dns01` challenge, and it populates the read-only `custom_domain_address` (plus `mirror_custom_domain_address` on the `.darkube.ir` mirror). Backs `set subdomain`; `set domain --add` refuses a platform subdomain up front and names the command that works.
  - `creation_method` — how the app came to exist, and **the field that distinguishes a managed service from a plain workload**. There is no separate managed-services API: a oneclick Redis, Postgres, Grafana or Prometheus is an ordinary app in `/api/v2/darkube/apps/` whose `creation_method` names the service. Probing for a dedicated endpoint on 2026-08-28 found nothing — `oneclicks`, `services`, `managed`, `managed_services`, `marketplace`, `charts`, `chart_apps`, `addons` and `databases` all 404 on both v1 and v2. The full enum, from `OPTIONS /api/v1/darkube/apps/`: `confluence, docker_image, elasticsearch, file_upload, gitlab_runner, git_repo_url, grafana, jira, jirasm, jupyter, kafka, kibana, keycloak, mariadb, metabase, minio, minionew, mongodb, mssql, mysql, nextcloud, nginx, postgresql, postgresqlnew, prometheus, pyroscope, rabbitmq, redis, redisnew, stolon, rocketchat, wordpress, kenar_divar`. `get apps -o wide` prints it as TYPE, `--type` filters on it, and `--managed` selects everything that is not `docker_image`/`git_repo_url`/`file_upload`.
  - Git build fields — `git_repo_url`, `git_branch_name`, `git_provider_type` (`Github`|`Gitlab`), `git_build_dockerfile`, `git_build_context`, `git_build_workdir`, `git_build_args`, `autodeploy_on_git_push`, `build_method` (`gitlabci`|`webhook`), `builder` (`dockerfile`|`heroku_buildpacks`). Set `creation_method: git_repo_url` and omit `image_repo`/`image_tag` — Darkube builds the image, pushes it to `registry.hamdocker.ir/<tenant>/<app>` and fills those in itself, tagging `<commit>-<app-id-prefix>`. **Creating one has an account-level prerequisite**: the provider must be connected to the Hamravesh account, or the API answers `400 GithubAuthException` / `GitlabAuthException` ("install the Darkube app in your account's Integration section"). Confirmed 2026-08-28 — the payload validated and reached the authorization check.
  - `OPTIONS` on the **list** route is the cheapest schema reference there is: it returns `actions.POST` with every field, its type, and the `choices` for each enum. That is where the `creation_method`, `builder`, `build_method`, `git_provider_type`, `plan_type` and `ingress_controller_type` value sets above came from.
  - `trigger_deploy_token` — the app's CI deploy token, the `--token` half of `darkube deploy --app-id <id> --token <tok>`. Read-only as far as anyone has tried, present on the v2 detail, and stored nowhere in the cluster, so the API is the only way to wire up a pipeline without the console. `get deploy-token` prints it; it is deliberately **not** a field on the `App` struct, or `get apps -o json` would dump every app's token.
  - `namespace.cluster.has_capacity_to_create_app` — whether the cluster will accept a new app at all. Worth checking before a create: as of 2026-08-11 `hamravesh-c13` reports `false` while `hamravesh-c11` reports `true`.
- **Three endpoints are not tenant-scoped**, verified 2026-08-24 with a JWT and no `X-Organization` header: `/api/v2/users/profile`, `/api/v1/notifications/all_list/` and `/api/v1/darkube/plans/` all answer 200, while `/api/v1/darkube/namespaces/`, `/api/v2/darkube/apps/` and `/api/v1/darkube/certificates/` answer 403 `permission_denied` and `/notifications/alerts/api/alerts/` answers 400 `["Organization is required. Please provide x-organization header."]`. That is why `cmd.newGlobalClient` exists alongside `cmd.buildClient`: `whoami`, `get notifications` and `get plans` build through it and work before any tenant is selected, which matters because `whoami` is the only way to learn the tenant slugs in the first place — gating it on a tenant made the first run a chicken-and-egg. Every other command still fails fast with `errNoTenant` instead of sending a request the API would reject.
- **`POST /api/v1/token/refresh/` is intermittently unreliable.** It returns 500s and bare EOFs often enough to make the whole CLI look broken, because every tenant-scoped command mints an access token first — observed repeatedly on 2026-08-27, where the identical command succeeded seconds later each time. `auth.Client.Refresh` therefore retries transient failures (transport errors and 5xx) with linear backoff, and fails fast on 4xx, since an expired refresh token never becomes valid by waiting. Do not "fix" a flaky command by re-running it by hand; if a new code path is failing here, check whether it is bypassing that retry.
- The JWT is a Console SimpleJWT access token: short-lived (~8h) and **IP-bound** (an `ip` claim), so it must be minted on the machine that connects. The refresh token is long-lived.
- DRF conventions: list envelope `{count,next,previous,results}`; error envelope `{detail,success,code}`. Numeric-looking fields can be strings with units (`ram_limit:"500M"`, `cpu_request:"250m"`).

## Confirmed vs unverified

Confirmed against a live session:

- **2FA login** — `POST /api/v1/token/` with `{email,password}` and the TOTP in the `x-otp` header works (`darkubectl login`).
- **Exec frame protocol** — the Kubernetes remotecommand channel protocol: binary frames prefixed with a 1-byte channel id (0 stdin, 1 stdout, 2 stderr, 3 exit-status → ends the session, 4 resize as `{"Width","Height"}`). See the channel constants in `internal/wsexec`.
- **REST `Bearer` auth** — `Authorization: Bearer <jwt>` works for the whole REST API (the `ip` claim is not enforced for REST). The Api-key and the Console login are different principals with different per-app access, so the login is the full-access path.
- **`GET /api/v1/darkube/namespaces/`** — works with a JWT, 200 with the full project list including empty projects. Confirmed 2026-08-11.
- **`GET .../app_log/`** — confirmed against running apps, including a pod that was not Ready. This is the only diagnostic that works on a failing container: the exec websocket 403s unless the pod is Ready, so `logs` is what you reach for when an app will not start.
- **The websocket subprotocol is not a selector.** `/ws/aexec/`, `/ws/app-pods/` and `/ws/app-state/` each accept `terminal`, `json`, `logs` or `log` interchangeably — only the 2nd (token) and 3rd (org) values matter. Unknown `/ws/…` paths return 500 on the handshake rather than 404, so a 500 there means "no such route", not an outage.

- **`POST` accepts the full app shape** — `svc.ports`, `disk` and `envs` all persist when sent at creation. Verified 2026-08-11 by creating throwaway apps and reading each field back, including a `rawfile-btrfs` PVC that bound and came up healthy on c11.

Corrected 2026-08-23 — **`PATCH` is not broken, it is not implemented, and `PUT` works.**

- `OPTIONS` on the v1 app detail returns `{"actions": ["PUT"]}`, and on the v2 detail returns no write actions at all: the viewset defines `update` but not `partial_update`. The bodyless 500 every PATCH returns is that missing code path crashing, not a server fault — which is why no field ever worked and why both API versions behaved identically.
- `PUT /api/v1/darkube/apps/<uuid>/` returns **202** and the change sticks. Verified end to end against a throwaway app in the `rahacloud` test org on 2026-08-23: `replicas` 1→2, `envs` added and removed, `external_hosts` added and removed, `enable_SSL` toggled, and `custom_config.hpa` set (with `is_hpa_enabled` flipping to match). See `client.UpdateApp` for the required normalization.
- **A PUT that omits `secret_envs` preserves them.** Verified explicitly, because the whole read-modify-write design depends on it: an app created with two secret envs still had both after a PUT whose body dropped the field. Secrets are read-only on this serializer, so omitting is the safe move and echoing the (value-less) read back is not.
- Consequently `scale app` and `patch app` now work — `patch` is a client-side merge into the full object followed by a PUT, so a concurrent console edit between the read and the write is lost. `set env` and `set domain` are built on the same path.

Still true, confirmed 2026-08-11:

- **Delete is asynchronous and can orphan the release.** After `DELETE` the app leaves the list immediately, but its Helm release is removed separately and may not be removed at all. Recreating under the same name then fails: `TerminatingAppException` ("try again in a minute") while the delete is in flight, and `SameHelmReleaseNameExists` indefinitely if the release was left behind. There is no way out through the API — no `force`/`overwrite`/`adopt_existing` flag on create, no `helm_release_name` override, and no release endpoint (all 404). Clearing an orphan needs the Darkube console or Hamravesh support. **This is the common case, not the edge case**: of the thirteen Deployments in `talaland-dev` on 2026-08-18, ten were orphans — every app deleted from that namespace had left its release running, some for over a week. `get orphans` exists to find them, since neither the API nor the cluster shows the divergence on its own. The API distinguishes the two collisions itself: `DuplicateReleaseAndNamespaceException` means a live app really does hold the name, `SameHelmReleaseNameExists` means only a release does — `cmd.explainCreateError` turns both into English guidance on stderr. Now that apps can be edited in place, prefer that over delete-and-recreate, which is what strands releases in the first place.

Not verified:

- Whether the two throwaway apps deleted from `rahacloud` on 2026-08-23 orphaned their releases — that needs `kubectl` against `hamravesh-c11`, which this machine does not have.
- Whether `/api/v2/users/profile` works with an Api-key. It is confirmed with a JWT only; `client.OrganizationID` keeps the old app-detail derivation as a fallback for that reason. The same gap applies to the tenant-free probe above — it was run with a JWT, so an Api-key may still be refused on those three endpoints for a different reason than the missing header.

`create app` requires the JWT (the Api-key lacks the user context and 500s). Its numeric `organization` field comes from `/api/v2/users/profile` (`client.OrganizationID`), which matters because the old derivation — reading it off an existing app's v1 detail — cannot work in an organization that has no apps yet, making it impossible to create the *first* app in a new tenant. That path is kept only as a fallback.

## Conventions

- Keep `golangci-lint` at **0 issues**. `.golangci.yml` runs `default: all` with a few opinionated linters disabled and scoped exclusions — the comments there explain each; prefer fixing code over adding disables.
- Prefer fixing the real finding; when a rule is a false positive, use a targeted `//nolint:<linter> // reason` rather than disabling it globally.
- Markdown is linted by markdownlint (`.markdownlint.jsonc`, `MD013` off). Run `npx markdownlint-cli2 <file>` after editing docs.
- **Markdown is written one paragraph per line**, `README.md` and this file included. Do not hard-wrap prose: each paragraph, and each list item including its continuation, is a single physical line, however long. `MD013` is off precisely so this is allowed. Reflowing to a column width produces a diff touching every line of a paragraph for a one-word change, which is what this avoids. Code fences, tables and the HTML header block are exempt — leave their line structure alone.
- Never persist secrets beyond the 0600 config file; never log tokens (the `--debug` frame dumper logs terminal I/O, not credentials).
- The README banner is hand-authored SVG. `assets/banner.svg` and `assets/banner-dark.svg` are the same drawing and differ only in the `.wordmark`/`.tagline` fills, so edit one and port the change; `assets/social-preview.svg` is that drawing on an opaque 1280x640 frame for GitHub's social-preview slot, and `assets/social-preview.png` is rendered from it with `rsvg-convert -w 1280 -h 640 assets/social-preview.svg -o assets/social-preview.png` — regenerate it whenever the SVG changes, since GitHub only accepts the raster. Colors are taken from `internal/output/palette.go` so the banner shows the real output, not an invented palette.
- Commit messages end with the trailer `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`.
